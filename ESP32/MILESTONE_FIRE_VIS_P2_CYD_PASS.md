# FIRE-VIS-P2 — quatre phases originales, rendu additif, cadence 375 ms : PASS CYD borné

**Date :** 22 novembre 2026. **Issue :** [#416](https://github.com/Kharn27/DoomRPG-RE/issues/416). **PR :** [#421](https://github.com/Kharn27/DoomRPG-RE/pull/421). **Branche testée (selon le contexte utilisateur) :** `agent/esp32-fire-vis-p2-phase-cadence`, candidat de code `018acd153495386cf5e18814b10dda5ad6c7293f`. **Attention :** le log Serial ne contient aucun SHA de binaire ; l'identité exacte du firmware flashé est attribuée au contexte de test et **non vérifiée cryptographiquement**.

## Décision architecturale : accepter les phases sautées

La correction P1 [#417](https://github.com/Kharn27/DoomRPG-RE/pull/417) restitue le mode **7 additif RGB565 saturé** des entités feu (`eType == 10`, non-CROSS), sans alpha arbitraire à 50 %. Les quatre **images originales** de feu du PAK sont distinctes : `logical=129`, bitshapes `actual=382,383,384,385`, établies par décodage offline direct du PAK utilisateur (cf. détails offsets, masques, signatures SHA256/FNV dans la PR #421). Les quatre valeurs `phase=0..3` restent choisies à la cadence originale **250 ms** du calcul de `EspNativeAmbientSprite_frame()`, avec décalage temporel par index.

La première proposition P2 tentait d'imposer un redraw autonome lors de **chaque** frontière de phase 250 ms. Le test CYD et la comparaison visuelle ont confirmé l'affichage physique des quatre images, mais l'utilisateur a signalé une **réactivité tactile sensiblement dégradée**. Ce compromis a été rejeté. La correction finale retire **l'ordonnanceur fire-only 250 ms** et remet les feux rasterisés dans la famille rapide partagée **375 ms**, sans boucle FPS fixe, sans accumulation de frames en retard, et sans second framebuffer. Les autres animations (monstres rapides 250 ms, monstres ordinaires 4000 ms, portes, murs, CROSS et glow) restent inchangées. Lorsqu'un MOVE/TURN provoque un rendu, il échantillonne directement la phase courante ; en repos, des phases intermédiaires peuvent être sautées. **L'objectif final est une fluidité du gameplay acceptable, pas 100 % des phases diffusées sur le LCD.**

Les témoins `[FIREVIS-P2] PRESENT` ne sont émises qu'après une présentation LCD réelle réussie, sont bornées à **48 lignes**, et mesurent `observedMs` après la pompe audio, **pas** le temps exact d'apparition sur l'écran. Elles couvrent les rendus de jeu stabilisés et les prévisualisations publiées, pas un enregistrement exhaustif de tous les sprites.

Firmware normal `esp32-cyd` sur **ESP32-D0WD-V3 240 MHz, 4 MiB flash, sans PSRAM**, framebuffer **160×120 RGB565 / 38 400 B**, écran 320×240 ×2. Démarrage, menu, **LOAD V11 slot09 (5 604 B) → Entrance**, jeu, HUB/System EXIT → menu.

- **Rendu flamme :** **48** témoins `FIREVIS-P2 PRESENT` post-écran, dont **24** rendus avec `preview=0`. Ils contiennent les **quatre** phases 0,1,2,3 et les quatre bitshapes 382,383,384,385 ; indices BSP variés 74/139/135/85. Les `phaseSteps` peuvent être 0,1 ou 2 : les sauts font partie du compromis décidé.
- **Interaction :** **26** commandes tactiles `RESIDENTGAMEPLAY QUEUE` ; **12 MOVE** validés, **4 TURN** validés, **5 FIRE-COMMIT** (flammes éteintes), **2 DOORANIM COMPLETE** (ouverture + fermeture avec HOLD/RELEASE). Le testeur confirme « Ça m'a l'air ok » sur la réactivité en jeu. Cette appréciation n'est **pas** un histogramme de latence tactile ni une preuve d'absence de tous les appuis manqués.
- **Performances dans ce parcours :** **39** `RA2B FRAME`, moyenne **~108 ms** (`totalUs`, min ~49 ms, max ~139 ms), **20** `VIEWANIM FRAME`, moyenne **~102 ms** (min ~91 ms, max ~134 ms). Aucun panic/WDT, `FAIL-HEAP` ou corruption de ressource visible.
- **Musique/SFX :** musique `M_STALKS.wav` du LOAD `PRESTART ready=1 failClosed=0`. **Deux `ENTRANCEMUSIC FINAL`**, menu et gameplay, `underruns=0`, `recoveries=0`, `gapsOver500Ms=0`. ## Vérifications automatiques et intégration

- Les tests P1 couvrent le routage additif sur les vrais corps C, masques/saturation et non-feux. P2 `native_fire_vis_p2_host.py` compile **les vrais corps C** `ambientDue/suspend/reset` ; vérifie calcul quatre phases 250 ms, **absence de redraw feu à 250/374 ms**, demande à 375 ms, et familles rapides/lentes et suspension `fail-closed`.
- L'oracle historique `sdl_f28_native_render_intro_header_host.py` conserve l'empreinte immuable du renderer antérieur ; changements P2 inversés précisément dans le test d'archive. Aucun test de lecture PAK synthétique ou lecture ZIP runtime ajouté.
- Double CI **SUCCESS** sur le candidat 375 ms testé (push [#44989761964](https://github.com/Kharn27/DoomRPG-RE/actions/runs/44989761964), PR [#44989767313](https://github.com/Kharn27/DoomRPG-RE/actions/runs/44989767313)), avec firmware normal/inverted/bringup/trace et oracles ELF.
- Après test, la branche a incorporé `main=2758ea343720bdec81efa2d7a0638c26cf0e7755` (ARCH-RC24) par **merge de synchronisation** `d67d7901abfcc30713bc90391645bf5bd3aa3109`. Les seuls changements P2 préservés dans le résultat de ce merge sont les sept sources/tests P2 et l'ajout isolé d'une commande à CI ; le firmware combiné **n'a pas été reflashé** sous ce nouveau SHA. La CI d'intégration combinée fait foi pour la compilation; ne pas prétendre de nouveau PASS physique sur le SHA de merge.

## Limites / clôture bornée

Le test a exercé Entrance avec quelques feux visibles, leurs frames, cinq extinctions, portes, rotations/déplacements, LOAD, HUB EXIT, musique et SFX. Il ne démontre **pas** une parité pixel-à-pixel avec le legacy, un A/B de latence mesuré sous protocole rigide, l'occlusion de chaque feu sur chaque map, un changement de carte, un combat de monstre dans **cette** capture, un menu automap exhaustif, ni un essai d'endurance de plusieurs heures. Le smoke-test indépendant de RC24 sur CYD couvrait déjà beaucoup d'autres interactions (sprites/glows, combats, UI), mais pas le **HEAD combiné** FIRE-P2+RC24 exact. Ces lacunes non bloquantes ne doivent pas être renommées en tests réussis.

Le choix final de la campagne [#416](https://github.com/Kharn27/DoomRPG-RE/issues/416) reste **fidélité du mode 7 / quatre vrais assets / redraws bornés 375 ms / priorité utilisateur**. Un alpha-blending 50 % n'est pas une condition de clôture : ce serait une variante artistique distincte. Sujets de latence générale/police [#420](https://github.com/Kharn27/DoomRPG-RE/issues/420) et audio première arme [#419](https://github.com/Kharn27/DoomRPG-RE/issues/419) hors FIRE-VIS.
